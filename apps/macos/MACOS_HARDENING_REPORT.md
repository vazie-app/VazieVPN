# Vazie VPN для macOS: отчёт об укреплении безопасности и надёжности

Дата: 2026-10-20. Версия кода: рабочее дерево `Apps/vpn/apps/macos` (не закоммичено).

**Главное.** Корневой скрипт больше не запускается из `.app` и не доверяет ничему, что может записать пользователь. Конфиг Xray проходит allow-list внутри root-скрипта. Исходные DNS/IPv6 сохраняются на диск с подписью. Добавлены Kill Switch, автопереподключение, состояния `Reconnecting`/`Connection Lost` и честный `Connected`. Все автоматические тесты проходят (178, 3 пропущены как и раньше). **Но ни одна привилегированная часть не запускалась на настоящем macOS от root** — вы не разрешали это, и я ничего не менял в сети вашего Mac. Поэтому оценка внизу — **NO**.

```
│  networksetup → HTTP/HTTPS/SOCKS    │   (текст скрипта лежит ВНУТРИ исполняемого     │
│  PAC при split                      │    файла: TunScriptSource.swift)               │
└─────────────────────────────────────┼────────────────────────────────────────────────┘
                 один запрос пароля   ▼
┌─ /private/var/run/app.vazie.vpn.tun  (root:wheel 755) ───────────────────────────────┐
│  run.sh (0500) ─ копия Xray (0500, проверена) ─ cmd (FIFO, владелец пользователь)    │
│  status/info/pid (644, пишет root)                                                    │
│                                                                                       │
│  Супервизор (root): проверка движка → ждёт CONFIG → allow-list (JXA) → Xray (TUN)     │
│    → ifconfig utunNN → маршруты 0/1 + 128/1 + хост-маршрут до сервера                  │
│    → [pf-якорь com.apple/050.VazieVPN]  → DNS 1.1.1.1/1.0.0.1 + IPv6 Off для сервиса   │
│    → контрольный запрос через туннель → «running <nonce>»                             │
│  Следит за: родителем (тот же процесс), движком, якорем pf. STOP/смерть app → откат.   │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

* **Движок:** Xray-core v26.7.28 (бинарник, процесс), VLESS (REALITY/TLS, TCP/WS/gRPC, flow vision). Не Network Extension: нужен платный entitlement.
* **Системное туннелирование:** TUN-интерфейс, созданный самим Xray (от root), и маршруты, поставленные скриптом.
* **Режим по умолчанию в коде:** «Системный прокси» (как и раньше). «Весь Mac» включается пользователем.

## 4. Модель угроз

**Что защищаем:** (1) отсутствие root-эскалации через приложение; (2) VPN-ключи и адрес сервера; (3) отсутствие утечек трафика/DNS при включённой защите; (4) сеть Mac не остаётся в изменённом состоянии.

| Актор / сценарий | Что может | Как закрыто |
|---|---|---|
| Вредоносный процесс того же пользователя, подмена `.app`/скрипта/Xray | Подменить то, что запустит root | Root-скрипт не читается из бандла (в подписанном бинарнике); копия Xray проверяется (Team ID / SHA-256) |
| Тот же процесс: симлинки/гонки в каталогах | Заставить root писать/удалять чужие файлы | Нет файлов root в пользовательских каталогах; root-каталог; `mv` вместо записи через симлинк; `O_NOFOLLOW` |
| Тот же процесс: вредоносный конфиг в FIFO | `log.access` → запись файла; открытый прокси; unix-сокет | Allow-list, лимит размера, nonce |
| Другие локальные пользователи | Читать `info`/`status` | Нет секретов и адреса сервера; ключи не пишутся на диск |
| Подмена снимка DNS | Заставить восстановление выставить DNS злоумышленника | HMAC, проверка формата, карантин |
| Профиль/подписка со злым содержимым | Инъекция в команду/JSON | `JSONSerialization`, нет строковой сборки; аргументы root-скрипта валидируются; прошёл тест с `'; touch … ; '` |
| Сбой/краш/потеря питания/перезагрузка | Оставить DNS/IPv6/pf/маршруты | Снимок + `--recover` + баннер; pf и маршруты сбрасываются перезагрузкой |
| Сбой VPN-сервера/сети | Трафик уходит напрямую | Опциональный Kill Switch; состояния `Reconnecting`/`Lost`; нет «Connected» без проверки |

**Остаточный риск модели «запрос пароля»** (не исправлен, требует Developer ID): процесс пользователя может сам вызвать такое же окно пароля и запустить тот же супервизор с allow-listed конфигом, ведущим на сервер атакующего. Нужен ввод пароля пользователем. Закрывает привилегированный helper (`SMAppService` + XPC), привязанный к подписи приложения.

**Вне модели:** компрометация самого root, ядра, SIP; подписанный вредоносный Xray той же Team ID.

## 5. Поведение Kill Switch

Включается в Настройки → Kill Switch (только режим «Весь Mac», по умолчанию выключен, действует со следующего подключения).

* **Механизм:** pf-якорь `com.apple/050.VazieVPN`, подключённый системным правилом `anchor "com.apple/*"` в `/etc/pf.conf`. Основной набор правил не трогается, чужие якоря не трогаются, **глобальных flush нет**. `pfctl -E` / `-X <token>` (по ссылке). Сбрасываются только правила нашего якоря (`-a … -F rules`).
* **Разрешено:** `lo0`; интерфейс туннеля; одно исходящее TCP-соединение к `IP:порт` сервера на физическом интерфейсе; DHCP; локальные сети (`10/8`, `172.16/12`, `192.168/16`, `169.254/16`, `224/4`), но **DNS (порт 53) на физическом интерфейсе блокируется до этого правила**; IPv6 только link-local (`fe80::/10`, `ff02::/16`, ICMPv6 для NDP).
* **Блокируется:** всё остальное, IPv4 и IPv6 (`block drop quick all`). Все `pass` — `quick`.
* **Потеря движка:** якорь остаётся; приложение показывает «Заблокировано»/«Connection lost»; «Отключить» снимает блок и возвращает DNS/IPv6/маршруты.
* **Split + Kill Switch:** добавляется `pass out … user root` (сокеты Xray нужны для «direct» сайтов). Это значит, что другие root-процессы тоже проходят. Это **частичная** защита в этом режиме.
* **Проверка перед включением:** якорь реально оценивается системой (в основном наборе есть `anchor "com.apple/*"`) и правила загружены; иначе туннель не открывается (`Kill Switch could not be turned on`), а не «делает вид».
* **Сторожок:** раз в ~5 с проверяет, что правила на месте; снятые кем-то — возвращает; не вернулись — health `dead` → пересборка.

**Что Kill Switch НЕ делает (поэтому это не «полноценный постоянный kill switch»):**
1. Не переживает завершение приложения/перезагрузку Mac — блок снимается намеренно, чтобы не оставить Mac без интернета. Если приложение убито `kill -9`, супервизор замечает это в течение нескольких секунд и снимает блок. Если убит и сам супервизор (`SIGKILL`), блок остаётся, пока не нажать «Восстановить сеть» в приложении или не перезагрузить Mac.
2. Не защищает время до подключения и промежуток между загрузкой правил и установкой маршрутов.
3. Уже установленные pf-состояния чужих правил не сбрасываются (global flush запрещён). Если pf уже включён кем-то с `keep state`-правилами, старые соединения могут продолжиться.
4. Блокирует и другие туннели на физическом интерфейсе (Tailscale и т. п.).
5. Не проверялся на реальном pf (§9): синтаксис проверен `pfctl -n`, остальное — по заглушке.

## 6. Поведение Auto Reconnect

Включён по умолчанию (Настройки → Переподключаться автоматически). Любое действие происходит только при «намерении» пользователя: Connect ставит его, Disconnect снимает и отменяет всё.

| Событие | Реакция |
|---|---|
| Xray упал / супервизор сообщил `lost` (опрос статуса раз в секунду) | `Reconnecting (n)` → попытка с backoff |
| Два подряд неудачных health-запроса (проверка раз в ~18 с, значит до ~36 с) | Потеря → reconnect (один сбой — не потеря) |
| Маршрут в туннель не тот (`route get 1.1.1.1` ≠ tun) | Потеря сразу |
| Смена шлюза / Wi-Fi ↔ Ethernet (`NWPathMonitor` + `netstat`, debounce 1 с) | Потеря → reconnect |
| Сеть пропала | `No internet`, попытки **не тратятся**; при возвращении сети счётчик с нуля |
| Сеть вернулась под живым туннелем | Сначала проверка, потом «Connected» |
| Wake после сна | Пауза 2 с, проверка (и второй взгляд через 1.5 с), затем reconnect при необходимости |
| Сервер недоступен | Backoff `1, 2, 4, 8 … ≤30 с ±20 %`, максимум 8 попыток, затем `Connection Lost` и ожидание пользователя; сеть/Wake/кнопка «Переподключить» сбрасывают счётчик |
| Режим «Весь Mac», супервизор жив | Движок перезапускается **в том же супервизоре, без нового пароля** |
| Режим «Весь Mac», супервизор мёртв | Автоматически не переподключается (нужен пароль): `Connection Lost`, кнопка «Переподключить» |
| Нефатальные ошибки (`handshake`, `network`, `routes`, `dns`…) | Повторяются |
| Фатальные (`engine`, `integrity`, `unsupported`, `proxyTaken`, `adminDenied`, `killSwitch`…) | Останавливает цикл |

Защита от гонок: одно поколение (`generation`), один `reconnectTask`; callback'и привязаны к экземпляру туннеля (а не к номеру); тест «Connect и Disconnect одновременно» (12 итераций) проверяет, что остаётся ровно один живой туннель или ни одного.

## 7. Восстановление DNS, IPv6 и маршрутов

Три слоя, от быстрого к аварийному:

1. **Супервизор при штатном стопе / смерти приложения / смерти Xray:** откат маршрутов (только добавленных им), pf-якоря (`-F rules`, `-X token`), DNS и IPv6. DNS/IPv6 возвращаются **только если до сих пор наши** (`DNS == 1.1.1.1 1.0.0.1`, IPv6 `Off`); если пользователь или другая программа изменили — не трогаются.
2. **Снимок в приложении** (`network-snapshot.json`): пишется до любого изменения; подписан HMAC; проверяется тип/владелец/права/значения; при подозрении уходит в `.bad`. На запуске и после каждого туннеля `reconcile` возвращает то, что осталось (например, после перезагрузки: DNS `1.1.1.1` без процесса). Если системный `networksetup` откажет без прав, предлагается одна команда в окне пароля (значения предварительно валидированы).
3. **Аварийный `--recover`** (одно окно пароля, кнопка «Восстановить сеть» на главном экране): убивает остаточный Xray (только если его командная строка — наш бинарник), сбрасывает наш якорь, снимает маршруты, возвращает DNS/IPv6 из root-записи `net.state`.

Перезагрузка с активным VPN: маршруты и pf очищаются системой; DNS/IPv6 остаются, но их возвращает снимок при первом запуске (баннер/тихо). Идемпотентность проверена: повторный cleanup/recover ничего не делает.

## 8. DNS и IPv6

* **Системные и scoped-резолверы:** на живой системе (до изменений) `scutil --dns` показывал нескопированный `1.1.1.1/1.0.0.1` и scoped-резолвер на `en1` с тем же адресом. Egress DNS подтверждён: запрос к `8.8.8.8` показывал клиентскую подсеть сервера VPN, не провайдера. **Scoped-запросы к `1.1.1.1` через `en1` без Kill Switch могут идти мимо туннеля** (приложения, привязывающие запрос к интерфейсу). Закрывается только pf (блокировка не-туннельного трафика на `en1`). Без Kill Switch остаётся остаточным риском.
* **UDP/TCP:** `network: tcp,udp`, порт 53 уходит в туннель в обоих режимах split. UDP через VLESS требует поддержки на сервере (не проверялось).
* **Split:** исправлена утечка DNS в «include» (D1). Лookup'ы идут через туннель независимо от правил доменов. Тест проверяет порядок правил.
* **DNS локальной сети:** под Kill Switch порт 53 на физическом интерфейсе блокируется (D3).
* **IPv6:** TUN-инбаунд Xray настроен только на IPv4, поэтому IPv6-трафик не может пройти через туннель и обошёл бы его. Обоснование отключения: для сервиса, чей интерфейс несёт туннель, IPv6 выключается на время работы туннеля и возвращается (если был «Automatic»); не глобально. Под Kill Switch IPv6 дополнительно режется pf. Результат `curl -6` с IPv4-mapped адресом (`::ffff:…`) в аудите **не** считался доказательством поддержки IPv6. Полноценная поддержка IPv6 в туннеле (маршруты `::/1` + `8000::/1`, IPv6-адрес tun, IPv6 на сервере) не реализована и перечислена в рекомендациях.
* **Остаточное:** DNS жёстко `1.1.1.1/1.0.0.1` (не берётся от сервера, нет DoH/DoT); IPv6 выключается только для основного сервиса; запрос имени сервера при самом первом подключении идёт системным резолвером (как у любого VPN).

## 10. Оставшиеся ограничения

1. Root-часть не проверена на реальном macOS от root (см. блокирующие проблемы).
2. Kill Switch не переживает выход приложения/перезагрузку (сознательно) и частичен в режиме split (§5).
3. Модель «окно пароля» остаётся уязвимой к фишингу процессом пользователя (§4). Нужен привилегированный helper с привязкой к подписи.
4. Доверие к подписи: с сертификатом Apple Development эта привязка слабее, чем с Developer ID + нотаризацией.
5. Загруженный (не встроенный) движок для Intel (`x86_64`) в режиме «Весь Mac» не поддерживается: хэш бинарника не закреплён. Встроенный подписанный — поддерживается.
6. Scoped DNS мимо туннеля без Kill Switch; DNS не от сервера; нет DoH/DoT.
7. IPv6 внутри туннеля не реализован; IPv6 отключается для основного сервиса на время работы.
8. Снимок DNS/IPv6 возвращает «наше» значение, но не отличит пользователя, который выставил в точности `1.1.1.1/1.0.0.1` после запуска VPN (возвращено будет прежнее значение). Крайне редкий случай.
9. Если запущены Ethernet и Wi-Fi одновременно, меняется только основной сервис.
10. Nonce/статус и все файлы в root-каталоге видны всем локальным пользователям (без секретов).
11. Уведомления (`Notifier`) не различают `Reconnecting`/`Lost`; их показывает только окно и меню-бар.

## 12. Рекомендации перед публичным релизом

1. Пройти M1–M13 на чистом Mac и на вашем (на Apple Silicon и Intel).
2. Сборка Developer ID + нотаризация; закрепить Team ID требованием `codesign -R` без запасного пути по хэшу в продакшене.
3. Заменить окно пароля на `SMAppService`-helper с XPC и проверкой подписи вызывающего (закрывает §4 «остаточный риск»), по возможности — постоянная блокировка по выбору пользователя на уровне helper.
4. Закрепить SHA-256 бинарника Xray для `x86_64`.
5. Добавить IPv6 внутри туннеля либо явно сообщать пользователю, что IPv6 отключён на время VPN.
6. Рассмотреть DoH/DoT или DNS, который отдаёт сервер, и убрать зависимость от `1.1.1.1`.
7. Независимый аудит (внешний) root-скрипта и allow-list конфига; fuzz-тест allow-list.
8. Нативные уведомления для `Connection Lost` / `Reconnecting`.
9. CI: запуск `swift test` и `shellcheck` (его на этой машине нет — не запускался), проверка соответствия `TunScriptSource.swift`.

## 13. Оценка

**READY FOR PUBLIC RELEASE: NO**

Блокирующие проблемы:

1. **Привилегированная часть не проверена на реальном macOS.** Особенно: `osascript -l JavaScript` под `do shell script … with administrator privileges` (если не заработает — режим «Весь Mac» не откроется, безопасно, но бесполезно); права/владелец `/private/var/run/app.vazie.vpn.tun`; реальные `route`/`networksetup`/`pfctl -E`/`-X`. (M1)
2. **Kill Switch не проверен на реальном pf** (утечки IPv4/IPv6/DNS при включённой защите, `user root` в split, сохранение уже существующих состояний). Пока не пройдены M3–M4, M9 это нельзя называть полноценной защитой. (M3, M4, M9)
3. **Нет Developer ID + нотаризации**; trust anchor на dev-сертификате слабее, а окно пароля уязвимо к фишингу процессом пользователя (§4). Для публичного релиза нужен helper, привязанный к подписи.
4. **Intel:** TUN-режим со скачанным движком не работает без закреплённого хэша.
5. **Интерфейс визуально не проверен**, нет снимков экрана.

Не блокирует, но важно: режим «Системный прокси» остался как был и по умолчанию безопаснее для публичного выпуска; «Весь Mac» стоит держать как бета-опцию до закрытия пунктов 1–4.
